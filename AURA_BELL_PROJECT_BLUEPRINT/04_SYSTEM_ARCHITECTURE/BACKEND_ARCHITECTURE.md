# Aura Bell — Backend Architecture (ব্যাকএন্ড আর্কিটেকচার)

## ১. ব্যাকএন্ড ডিজাইন প্যাটার্ন
FastAPI অ্যাপ্লিকেশনটি পরিষ্কার লেয়ার্ড আর্কিটেকচার (Layered Architecture) অনুসরণ করবে:

```text
HTTP Request
     ⬇️
API Router (/api/v1/...) [Pydantic Input Validation]
     ⬇️
Service Layer [Business Rules & Domain Logic]
     ⬇️
Repository Layer [SQLAlchemy / Database Queries]
     ⬇️
PostgreSQL Database (ACID Commit)
```

## ৩. হাইব্রিড লোকাল-ফাস্ট — ব্যাকএন্ড দায়িত্ব (টার্গেট আর্কিটেকচার)

হাইব্রিড লোকাল-ফাস্ট আর্কিটেকচারে ব্যাকএন্ডের দায়িত্ব নিচের অনুযায়ী বসবে:

* **সার্ভার অথরিটি**: পণ্য, মূল্য, ইনভেন্টরি, অর্ডার, পেমেন্ট, ব্যবহারকারী অ্যাকাউন্ট এবং অর্ডার স্টেটের চূড়ান্ত প্রাধিকার সার্ভারে থাকবে।
* **অথরিটেটিভ মূল্য ও ইনভেন্টরি ভ্যালিডেশন**: চেকআউটের সময় ব্যাকএন্ড ডাটাবেজ থেকে অ্যাক্টিভ মূল্য ও স্টক পুনর্বিবেচনা করবে।
* **আইডেমপোটেন্ট মিউটেশন**: ক্লায়েন্ট-জেনারেটেড মিউটেশন আইডেন্টিফায়ার ব্যবহার করে ডুপলিকেট অনুরোধ প্রতিহত করা হবে। (অ্যাক্সেক্ট প্রোটোকল ইমপ্লিমেন্টেশন ফেজে সিদ্ধান্ত নেওয়া হবে।)
* **রিটারাই-সেফ অপারেশন**: অনলাইন হলে পেন্ডিং মিউটেশন সিঙ্ক করার সময় রিটারাই-সেফ আচরণ নিশ্চিত করা হবে।
* **সিঙ্ক রিকোয়েস্ট হ্যান্ডলিং**: ক্লায়েন্ট থেকে আসা পেন্ডিং মিউটেশন সিঙ্কের জন্য ব্যাকএন্ডে রিকোয়েস্ট প্রসেসিং লেয়ার থাকবে। (এক্সাক্ট এন্ডপয়েন্ট অপরিবর্তিত থাকবে।)
* **মিউটেশন রিকনসিলিয়েশন**: ক্লায়েন্ট লোকাল স্টেট এবং সার্ভার স্টেটের Conflicts সার্ভার সাইডে হ্যান্ডল করা হবে। bijনেস-ক্রিটিক্যাল ডেটার ক্ষেত্রে সার্ভার অথরিটি থাকবে।
* **সার্ভার-সাইড Konflikt Handling**: Bijনেস-ক্রিটিক্যাল Conflicts-এ সার্ভারের সিদ্ধান্তই চূড়ান্ত হবে।

বর্তমান লেয়ার্ড আর্কিটেকচার (API Router → Service Layer → Repository Layer → PostgreSQL) বজায় থাকবে।
