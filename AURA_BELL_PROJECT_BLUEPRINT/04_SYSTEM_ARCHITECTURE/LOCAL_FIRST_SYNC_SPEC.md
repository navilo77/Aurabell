# Aura Bell — Local-First Sync Specification (লোকাল-ফার্স্ট সিঙ্ক স্পেসিফিকেশন)

> **স্থিতি**: ড্রাফট (Draft)। এই নথিটি এখনো অনুমোদিত নয়। ইমপ্লিমেন্টেশন পর্যায়ে ওনার অনুমোদন ছাড়া কোনো প্রস্তাবিত সিদ্ধান্তকে ফাইনাল মনে করা যাবে না।

---

## ১. উদ্দেশ্য ও পরিধি (Purpose & Scope)

এই নথি Aura Bell-এর হাইব্রিড লোকাল-ফার্স্ট আর্কিটেকচারের সিঙ্ক লেয়ারের **ডিজাইন-স্তরের** স্পেসিফিকেশন। উদ্দেশ্য হলো ক্লায়েন্ট-সাইড IndexedDB লোকাল ক্যাশ/পারসিস্টেন্স এবং সার্ভার-অথরিটেটিভ Supabase PostgreSQL ডাটাবেজের মধ্যে পেন্ডিং মিউটেশন সিঙ্ক, কনফ্লিক্ট রেজলিউশন, রিট্রাই নীতিমালা, অথেনটিকেশন/সেশন প্রভাব এবং কোটা/ইভিকশন সীমাবদ্ধতার কার্যপ্রণালী উপস্থাপন করা।

**অ-পরিধি (Out of Scope):**
- সোর্স কোড পরিবর্তন (নথি-শুধুমাত্র)
- IndexedDB ইমপ্লিমেন্টেশন
- সার্ভিস ওয়ার্কার / ব্যাকগ্রাউন্ড সিঙ্ক ইমপ্লিমেন্টেশন
- API এন্ডপয়েন্ট তৈরি (`/sync`, `/batch-sync`, `/reconcile` ইত্যাদি এখনো ফাইনাল নয়)
- ডাটাবেজ মাইগ্রেশন বা স্কিমা পরিবর্তন
- টোকেন/সেশন স্টোরেজ ফাইনালাইজ করা (IndexedDB / মেমোরি / কুকি) — অনিশ্চিত
- Conflict detection / merge অ্যালগরিদম ফাইনালাইজ করা

নিচের নীতিগুলো ADR-011, `PROJECT_BRAIN.md` (ধারা ৩.১), `FRONTEND_ARCHITECTURE.md`, `DATABASE_ARCHITECTURE.md`, `SECURITY_ARCHITECTURE.md` এবং `AUTHENTICATION_AUTHORIZATION.md` থেকে নেওয়া:

2. **IndexedDB হলো ক্যাশ/পারসিস্টেন্স লেয়ার**, বিজনেস-অথরিটেটিভ ডাটাবেজ নয়। **(APPROVED)**
3. **চূড়ান্ত প্রাধিকার**: চেকআউট, পেমেন্ট, মূল্য ভ্যালিডেশন, স্টক ভ্যালিডেশন ও অর্ডার কনফার্মেশনের শেষ প্রাধিকার সার্ভারে। **(APPROVED)**
4. **ক্লায়েন্ট-সাইড স্টেট কখনোই সার্ভার অথরাইজেশন বা বিজনেস ভ্যালিডেশন বাইপাস করবে না।** **(APPROVED)**

## ৪. বর্তমান ইমপ্লিমেন্টেশন (Current Implementation)

- বর্তমানে Zustand/Context এবং localStorage-ভিত্তিক কার্ট পারসিস্টেন্স আছে।
- IndexedDB, মিউটেশন কিউ, অফলাইন সিঙ্ক, রিট্রাই লজিক এবং কনফ্লিক্ট রেজলিউশন **ইমপ্লিমেন্ট করা হয়নি**।
- সমস্ত বিজনেস-ক্রিটিক্যাল অপারেশন (চেকআউট, পেমেন্ট, মূল্য ভ্যালিডেশন, স্টক ভ্যালিডেশন, অর্ডার কনফার্মেশন) শুধু সার্ভারে পরিচালিত হয়।

## ৫. লোকাল পারসিস্টেন্স লেয়ার (টার্গেট — PROPOSED DESIGN)

### ৫.১ IndexedDB কীভাবে কাজ করবে (কনসেপচুয়াল)

IndexedDB ক্লায়েন্ট-সাইড লোকাল ক্যাশ/পারসিস্টেন্স লেয়ার হিসেবে ব্যবহার হতে পারে। নিচের ডেটা লোকালি ক্যাশ/স্টোর করা যেতে পারে (কনসেপচুয়াল):

- ক্যাশড ক্যাটালগ, ক্যাটাগরি, ব্র্যান্ড
- ক্যাশড প্রোডাক্ট ডিটেইলস
- কার্ট ড্রাফট (শপিং কার্টের অস্থায়ী অবস্থা)
- wishlist / recently viewed
- পেন্ডিং অফলাইন মিউটেশন কিউ (মিউটেশন আইডেন্টিফায়ারসহ)

### ৫.২ সীমাবদ্ধতা (কী অথরিটেটিভ নয়)

নিচের বিজনেস-ক্রিটিক্যাল ডেটা লোকালি ক্যাশ করা গেলেও IndexedDB কখনোই অথরিটেটিভ রেকর্ড নয়:

- পেমেন্ট ডেটা (transaction state, webhook outcome)
- অর্ডার স্টেট (authoritative order status)
- বিজনেস-ক্রিটিক্যাল মূল্য (চেকআউটের সময় সার্ভার থেকে পুনরায় যাচাই হবে)
- বিজনেস-ক্রিটিক্যাল ইনভেন্টরি (চেকআউটের সময় সার্ভার থেকে পুনরায় যাচাই হবে)
- বিজনেস-ক্রিটিক্যাল অর্ডার স্ন্যাপশট

### ৫.৩ IndexedDB কোটা ও ক্যাশ ইভিকশন (UNRESOLVED)

- IndexedDB কোটা ব্যবস্থাপনা এবং ক্যাশ ইভিকশন পলিসি **অনিশ্চিত (UNRESOLVED)**।
- LRU (Least Recently Used) বা অন্য কোনো নির্দিষ্ট ইভিকশন কৌশল **ফাইনালাইজ করা হয়নি**।
- **বাধ্যবাধকতা**: যেকোনো ভবিষ্যৎ ইভিকশন কৌশলকে অবশ্যই প্রয়োজনীয় পেন্ডিং মিউটেশন সংরক্ষণ করতে হবে এবং ব্যবহারকারীর উদ্দেশ্যমূলক মিউটেশন নীরবে হারানো চলবে না।

## ৬. সিঙ্ক / মিউটেশন কিউ (টার্গেট — PROPOSED DESIGN)

### ৬.১ মিউটেশন কিউ কনসেপ্ট

অফলাইন-সক্ষম মিউটেশন পেন্ডিং অবস্থায় লোকাল কিউতে রাখা যেতে পারে। অনলাইন হলে পেন্ডিং মিউটেশন সার্ভারের সাথে সিঙ্ক করা যেতে পারে। রিট্রাই ও রিকনসিলিয়েশন কনসেপচুয়ালি ডকুমেন্ট করা হবে, কিন্তু এক্সাক্ট অ্যালগরিদম ফাইনালাইজ করা হবে না।

### ৬.২ সিঙ্ক প্রোটোকল ও এন্ডপয়েন্ট (UNRESOLVED)

- এক্সাক্ট সিঙ্ক প্রোটোকল (push / pull / delta) ইমপ্লিমেন্টেশন ফেজে সিদ্ধান্ত হবে।
- এক্সাক্ট সিঙ্ক এন্ডপয়েন্ট (`/sync`, `/batch-sync`, `/reconcile` ইত্যাদি) ফাইনালাইজ করা হবে না।
- পুশ/পুল ফ্রিকোয়েন্সি, ব্যাচ সাইজ এবং ডেল্টা সিঙ্ক কৌশল **অনিশ্চিত**।

### ৬.৩ আইডেমপোটেন্সি ও ডুপ্লিকেট প্রতিরোধ (PROPOSED / UNRESOLVED)

- ক্লায়েন্ট-জেনারেটেড মিউটেশন আইডেন্টিফায়ার / idempotency key ব্যবহার করে ডুপ্লিকেট অনুরোধ প্রতিরোধের **ধারণা** রাখা যেতে পারে। **(PROPOSED)**
- এক্সাক্ট আইডেমপোটেন্সি মেকানিজম (key generation, storage, server-side verification) ইমপ্লিমেন্টেশন ফেজে সিদ্ধান্ত হবে। **(UNRESOLVED)**

### ৬.৪ রিট্রাই নীতিমালা (PROPOSED DEFAULT ONLY — UNRESOLVED)

নিচের বিষয়গুলো **শুধুমাত্র প্রস্তাবিত/ডিফল্ট বিবেচনা**, ফাইনাল সিদ্ধান্ত নয়। ইমপ্লিমেন্টেশন ফেজে পরিবর্তনযোগ্য:

- `5xx` response পুনরায় চেষ্টা (retry) করা **যেতে পারে** (প্রস্তাবিত ডিফল্ট)।
- `4xx` response পুনরায় চেষ্টা করা **যাবে না** (প্রস্তাবিত ডিফল্ট)।
- Exponential backoff একটি **প্রস্তাবিত ডিফল্ট বিবেচনা**।

**অনিশ্চিত (UNRESOLVED):**
- রিট্রাই শ্রেণিবিন্যাস (কোন HTTP স্ট্যাটাস কোড রিট্রাইযোগ্য) — ফাইনাল নয়।
- ব্যাকঅফ প্যারামিটার (base delay, max delay, jitter) — ফাইনাল নয়।
- রিট্রাই লাইফসাইকেল (max retry count, সার্কিট ব্রেকার, failover আচরণ) — ফাইনাল নয়।
- রিট্রাই ব্যর্থ হলে চূড়ান্ত আচরণ — অনিশ্চিত।

## ৭. কনফ্লিক্ট ডিটেকশন ও রেজলিউশন (PROPOSED DESIGN + UNRESOLVED)

### ৭.১ বিজনেস-ক্রিটিক্যাল ডেটা (APPROVED)

বিজনেস-ক্রিটিক্যাল ডেটার (পণ্য, মূল্য, ইনভেন্টরি, অর্ডার, পেমেন্ট, অর্ডার স্টেট) ক্ষেত্রে সার্ভার অথরিটি থাকবে এবং সার্ভারের সিদ্ধান্তই চূড়ান্ত।

### ৭.২ নন-বিজনেস-ক্রিটিক্যাল ডেটা (PROPOSED / UNRESOLVED)

নন-বিজনেস-ক্রিটিক্যাল ডেটার ক্ষেত্রে merge / Last-Write-Wins (LWW) / custom reconciliation **মূল্যায়ন করা যেতে পারে**:

- **Last-Write-Wins (LWW) কে ইতিমধ্যে নির্বাচিত বলে ধরে নেওয়া যাবে না।** LWW শুধু একটি প্রস্তাবিত বিকল্প।
- এক্সাক্ট conflict detection অ্যালগরিদম **অনিশ্চিত (UNRESOLVED)**।
- এক্সাক্ট merge অ্যালগরিদম **অনিশ্চিত (UNRESOLVED)**।

### ৭.৩ কার্ট রিকনসিলিয়েশন (UNRESOLVED)

একাধিক ডিভাইসে বা অফলাইন-পরবর্তী কার্ট merge-এর এক্সাক্ট আচরণ, conflict detection এবং resolution নীতি ইমপ্লিমেন্টেশন ফেজে সিদ্ধান্ত হবে। **এই বিষয়ে LWW বা অন্য কোনো নির্দিষ্ট কৌশল নির্বাচিত বলে ঘোষণা করা হচ্ছে না।**

## ৮. অথেনটিকেশন ও সেশন (CONCEPTUAL ONLY)

### ৮.১ সার্ভার-অথরিটেটিভ অথেনটিকেশন (APPROVED)

Authentication/session handling সার্ভার-অথরিটেটিভ থাকবে। বিজনেস-ক্রিটিক্যাল অপারেশনের জন্য সার্ভারে JWT টোকেন ভ্যালিডেশন বাধ্যতামূলক।

### ৮.২ ক্যাশড ব্যবহারকারী-ফেসিং ডেটা (PROPOSED)

অফলাইন অবস্থায় ক্যাশড ব্যবহারকারী-ফেসিং ডেটা (যেমন প্রোফাইল, ক্যাশড অর্ডার হিস্ট্রি) অনুমোদিত offline strategy অনুযায়ী প্রদর্শন করা যেতে পারে।

### ৮.৩ অফলাইন সেশন / টোকেন (UNRESOLVED)

- অফলাইন সেশন / টোকেন সংরক্ষণ বা ব্যবহার করা হবে কি না — **অনিশ্চিত (UNRESOLVED)**।
- IndexedDB, মেমরি বা কুকিকে **ফাইনাল টোকেন-স্টোরেজ মেকানিজম হিসেবে ধরে নেওয়া যাবে না**।
- অফলাইন অথেনটিকেটেড API আচরণ **ফাইনালাইজ করা হবে না**।

## ৯. নিরাপত্তা সীমা (Security Boundary — রেফারেন্স)

`SECURITY_ARCHITECTURE.md` ধারা ৩ অনুযায়ী:

- IndexedDB / লোকাল স্টেট কখনো বিজনেস-ক্রিটিক্যাল ডাটাবেজের প্রতিস্থাপন নয় এবং কখনোই বিশ্বাসযোগ্য নয়।
- লোকাল ক্যাশে সংরক্ষিত ডেটা responsiveness ও offline continuity-এর জন্য ব্যবহার করা যেতে পারে, কিন্তু বিজনেস-ক্রিটিক্যাল অপারেশন চূড়ান্ত করার আগে সার্ভার ভ্যালিডেশন অপরিহার্য।
- সংবেদনশীল ডেটা (পেমেন্ট, অর্ডার স্টেট, মূল্য, ইনভেন্টরি) কেবল সার্ভারে সংরক্ষিত হবে; ক্লায়েন্টে শুধু ক্যাশড কপি থাকতে পারে, অথরিটেটিভ রেকর্ড নয়।
- Replay / idempotency, malicious client modification এবং offline mutation tampering প্রতিরোধ সার্ভার সাইডে এনফোর্স হবে; এক্সাক্ট মেকানিজম ইমপ্লিমেন্টেশন ফেজে সিদ্ধান্ত হবে।

## ১০. সার্ভিস ওয়ার্কার / ব্যাকগ্রাউন্ড সিঙ্ক (UNRESOLVED)

Service Worker / Background Sync strategy (offline sync trigger, periodic sync, network state API) ইমপ্লিমেন্টেশন ফেজে সিদ্ধান্ত হবে এবং **এখনই ফাইনালাইজ করা হবে না**।

## ১১. সিঙ্ক মিউটেশন লাইফসাইকেল (কনসেপচুয়াল — PROPOSED)

নিচের লাইফসাইকেলটি শুধু কনসেপচুয়াল (PROPOSED):

```text
Offline Mutation -> Local IndexedDB Queue (pending) -> Online হলে Server Sync -> Server Validation -> Success/Failure -> Local Queue থেকে সরানো / Retry Queue
```

এক্সাক্ট lifecycle state (pending -> syncing -> synced -> failed -> retry -> dead) এবং transition নিয়ম **অনিশ্চিত (UNRESOLVED)**।
