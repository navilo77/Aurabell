১. Database-এর উদ্দেশ্য
Aura Bell-এর Database এমনভাবে ডিজাইন করা হবে, যাতে একাধিক স্টোর, গ্রাহক, পণ্য, ইনভেন্টরি, অর্ডার, পেমেন্ট, ডেলিভারি ও ব্যবসায়িক হিসাব একটি কেন্দ্রীয় Database থেকে পরিচালনা করা যায়।
প্রাথমিক স্টোর:
1. Best Gadget।
2. Aura Skin Care।
প্রতিটি স্টোরের নিজস্ব পণ্য ও ব্যবসায়িক তথ্য থাকবে। তবে Customer, Cart, Checkout এবং Order Management কেন্দ্রীয়ভাবে পরিচালিত হবে।
১.১ মূল Database নীতিমালা
* PostgreSQL হবে মূল Database।
* প্রতিটি প্রধান Table-এ UUID Primary Key থাকবে।
* Date ও Time সংরক্ষণে TIMESTAMPTZ ব্যবহার হবে।
* অর্থের পরিমাণে NUMERIC ব্যবহার হবে, FLOAT নয়।
* সব গুরুত্বপূর্ণ Relationship-এ Foreign Key থাকবে।
* প্রয়োজনীয় Unique ও Check Constraint থাকবে।
* Stock Movement ও Financial Transaction-এর ইতিহাস সংরক্ষণ করা হবে।
* Database পরিবর্তন Migration-এর মাধ্যমে হবে।
* Production Database-এ সরাসরি অনিয়ন্ত্রিত পরিবর্তন করা যাবে না।

১৮. Database Transaction Rules
১৮.১ Checkout Transaction
একটি Checkout-এর মধ্যে:
1. Cart যাচাই।
2. Product ও Price যাচাই।
3. Stock Lock/Reservation।
4. Parent Order তৈরি।
5. Store Order তৈরি।
6. Order Items Snapshot তৈরি।
7. Order Address Snapshot তৈরি।
8. প্রয়োজনীয় Outbox Event তৈরি।
সব Database Operation সঠিকভাবে সম্পন্ন হলে Transaction Commit হবে।
কোনো গুরুত্বপূর্ণ Operation ব্যর্থ হলে Transaction Rollback হবে।
১৮.২ Payment Webhook Transaction
1. Webhook Signature যাচাই।
2. Event ID পরীক্ষা।
3. Event Record তৈরি।
4. Payment Status যাচাই।
5. Payment Transaction তৈরি।
6. প্রয়োজনীয় Order Update।
7. Outbox Event তৈরি।
8. Commit।
Duplicate Event এলে একই Financial Action দ্বিতীয়বার করা যাবে না।
১৮.৩ Refund Transaction
* Refund Amount যাচাই।
* পূর্বের Refund হিসাব করা।
* অনুমোদন যাচাই।
* Refund Request তৈরি।
* Provider Response সংরক্ষণ।
* সফল হলে Payment Status Update।
* Audit ও Outbox Event তৈরি।
External Provider Call এবং Database Transaction-এর মধ্যে ব্যর্থতা হতে পারে। তাই Refund-কে Retry ও Reconciliation-সমর্থিত Workflow হিসেবে তৈরি করতে হবে।
১৯. Row Level Security (RLS)
Supabase PostgreSQL-এ RLS ব্যবহার করা হবে।
প্রধান নিয়ম:
* Customer নিজের Profile দেখতে পারবেন।
* Customer নিজের Address দেখতে ও পরিবর্তন করতে পারবেন।
* Customer নিজের Order দেখতে পারবেন।
* Store Manager শুধু অনুমোদিত Store পরিচালনা করবেন।
* Inventory Manager অনুমোদিত Inventory পরিচালনা করবেন।
* Owner প্রয়োজনীয় অনুমোদিত সব Store পরিচালনা করতে পারবেন।
FastAPI-এর প্রতিটি Request-এ Authorization যাচাই করতে হবে।
RLS অতিরিক্ত সুরক্ষা; এটি Backend Authorization-এর বিকল্প নয়।
Database Migration ও প্রশাসনিক কাজের জন্য আলাদা নিরাপদ Server-side Permission ব্যবহার করতে হবে।

১. Database-এর উদ্দেশ্য
Aura Bell-এর Database এমনভাবে ডিজাইন করা হবে, যাতে একাধিক স্টোর, গ্রাহক, পণ্য, ইনভেন্টরি, অর্ডার, পেমেন্ট, ডেলিভারি ও ব্যবসায়িক হিসাব একটি কেন্দ্রীয় Database থেকে পরিচালনা করা যায়।
প্রাথমিক স্টোর:
1. Best Gadget।
2. Aura Skin Care।
প্রতিটি স্টোরের নিজস্ব পণ্য ও ব্যবসায়িক তথ্য থাকবে। তবে Customer, Cart, Checkout এবং Order Management কেন্দ্রীয়ভাবে পরিচালিত হবে।
১.১ মূল Database নীতিমালা
* PostgreSQL হবে মূল Database।
* প্রতিটি প্রধান Table-এ UUID Primary Key থাকবে।
* Date ও Time সংরক্ষণে TIMESTAMPTZ ব্যবহার হবে।
* অর্থের পরিমাণে NUMERIC ব্যবহার হবে, FLOAT নয়।
* সব গুরুত্বপূর্ণ Relationship-এ Foreign Key থাকবে।
* প্রয়োজনীয় Unique ও Check Constraint থাকবে।
* Stock Movement ও Financial Transaction-এর ইতিহাস সংরক্ষণ করা হবে।
* Database পরিবর্তন Migration-এর মাধ্যমে হবে।
* Production Database-এ সরাসরি অনিয়ন্ত্রিত পরিবর্তন করা যাবে না।

১৮. Database Transaction Rules
১৮.১ Checkout Transaction
একটি Checkout-এর মধ্যে:
1. Cart যাচাই।
2. Product ও Price যাচাই।
3. Stock Lock/Reservation।
4. Parent Order তৈরি।
5. Store Order তৈরি।
6. Order Items Snapshot তৈরি।
7. Order Address Snapshot তৈরি।
8. প্রয়োজনীয় Outbox Event তৈরি।
সব Database Operation সঠিকভাবে সম্পন্ন হলে Transaction Commit হবে।
কোনো গুরুত্বপূর্ণ Operation ব্যর্থ হলে Transaction Rollback হবে।
১৮.২ Payment Webhook Transaction
1. Webhook Signature যাচাই।
2. Event ID পরীক্ষা।
3. Event Record তৈরি।
4. Payment Status যাচাই।
5. Payment Transaction তৈরি।
6. প্রয়োজনীয় Order Update।
7. Outbox Event তৈরি।
8. Commit।
Duplicate Event এলে একই Financial Action দ্বিতীয়বার করা যাবে না।
১৮.৩ Refund Transaction
* Refund Amount যাচাই।
* পূর্বের Refund হিসাব করা।
* অনুমোদন যাচাই।
* Refund Request তৈরি।
* Provider Response সংরক্ষণ।
* সফল হলে Payment Status Update।
* Audit ও Outbox Event তৈরি।
External Provider Call এবং Database Transaction-এর মধ্যে ব্যর্থতা হতে পারে। তাই Refund-কে Retry ও Reconciliation-সমর্থিত Workflow হিসেবে তৈরি করতে হবে।
১৯. Row Level Security (RLS)
Supabase PostgreSQL-এ RLS ব্যবহার করা হবে।
প্রধান নিয়ম:
* Customer নিজের Profile দেখতে পারবেন।
* Customer নিজের Address দেখতে ও পরিবর্তন করতে পারবেন।
* Customer নিজের Order দেখতে পারবেন।
* Store Manager শুধু অনুমোদিত Store পরিচালনা করবেন।
* Inventory Manager অনুমোদিত Inventory পরিচালনা করবেন।
* Owner প্রয়োজনীয় অনুমোদিত সব Store পরিচালনা করতে পারবেন।
FastAPI-এর প্রতিটি Request-এ Authorization যাচাই করতে হবে।
RLS অতিরিক্ত সুরক্ষা; এটি Backend Authorization-এর বিকল্প নয়।
Database Migration ও প্রশাসনিক কাজের জন্য আলাদা নিরাপদ Server-side Permission ব্যবহার করতে হবে।
